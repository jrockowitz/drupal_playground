# #3279761: Plan for Schema.org Blueprints 1.0.0

## Context

- URL: https://www.drupal.org/node/3279761
- Status: Active; roadmap plan in `1.0.x-dev`.
- Lane: Roadmap maintenance and Drupal 11.2 modernization.
- Target branch: `1.0.x`.

## Evidence

- The plan predates the alpha releases and calls for stable-release scope, documented APIs, extensibility, tests, blockers, changelog, and shared maintenance ownership.
- The current public queue contains four open issues, verified 2026-09-09 with `drupalorg project:issues schemadotorg all --limit=100 --format=llm --no-cache`.
- Drupal core's duplicate hooks and programmatic JSON:API resource/relationship metadata both require Drupal 11.2.0: [duplicate hooks](https://www.drupal.org/node/3268812) and [JSON:API metadata](https://www.drupal.org/node/3280569).
- OOP hooks arrived in Drupal 11.1, but Drupal 11.2 provides the complete migration surface and the `module_name.skip_procedural_hook_scan` parameter. See [OOP hooks](https://www.drupal.org/node/3442349) and [procedural hook scan performance](https://www.drupal.org/node/3490771).
- The installed `1.0.x` checkout currently declares `^10.3 || ^11` in both `composer.json` and `schemadotorg.info.yml`; the workspace lock is Drupal 11.4.5. It contains 54 production `.module` files with procedural functions, and its remaining annotation-based plugin/entity definitions need an explicit Rector configuration and manual review. The [Rector issue](https://www.drupal.org/project/rector/issues/3265946) and [conversion guidance](https://drupal.stackexchange.com/questions/321008/how-to-use-drupal-rector-to-get-started-converting-annotations-to-attributes) confirm that annotation conversion is not a default set and must be selected per supported attribute.

## Proposed roadmap additions

### Drupal 11.2+ platform baseline

- Decision proposed: support Drupal 11.2+ only; change the root module's `composer.json` and `.info.yml` requirement after maintainer approval.
- Rationale: this is the first version that supports all planned platform APIs without compatibility shims. Continuing support for Drupal 10.3 and 11.0–11.1 would require `LegacyHook` forwarding functions/manual service definitions and would exclude duplicate hooks and JSON:API metadata.
- Compatibility consequence: document the dropped Drupal 10.3–11.1 support in release notes and the upgrade guide before a release.

### Duplicate hooks

- Implement `hook_entity_duplicate()` / `hook_ENTITY_TYPE_duplicate()` where duplication needs Schema.org mapping, field, or display follow-up.
- Add focused kernel coverage for a duplicate's mapping and related configuration behavior.

### Annotations to attributes

- Add an explicit, version-pinned Drupal Rector configuration for the three remaining annotation definitions; run it on a narrow path first.
- Review imports, translated attribute arguments, formatting, and discovery behavior manually; run the relevant tests and coding standards after each conversion.

### OOP hooks

- Run Rector, review every generated hook conversion, and fix all test failures.
- Move hook logic out of `src/{ModuleName}Manager.php` into appropriately named `src/Hook/{ModuleName}Hooks.php` classes; inject managers into those hook classes.
- Manually fix string translation and update `schemadotorg.api.php` examples/documentation.
- Retain procedural install/update hooks, and use `#[LegacyModuleImplementsAlter]` only where the remaining procedural meta hook requires it.
- Once the normal hooks are converted and verified, add `schemadotorg.skip_procedural_hook_scan: true` to the module service definition.
- Create an ADR stating that services provide reusable APIs and hook classes own Drupal alteration/integration behavior.

### JSON:API metadata

- Evaluate resource and relationship metadata needs in `schemadotorg_jsonapi`; use the new metadata events instead of overriding JSON:API internals.
- Add functional coverage proving the expected `meta` output and cacheability.

## Next action

Maintainer approval is required before changing the supported-core range or public API. If approved, make Drupal 11.2+ the release baseline, turn these roadmap entries into scoped work items, and sequence the OOP migration before enabling the procedural-scan optimization.
